## 1. 추진 배경과 현안

- 고객사에서 장비별로 요구하는 option(인터페이스 옵션)이 **15가지 정도** 정해져 있습니다.
- option별로 선택할 수 있는 항목은 **2~5가지씩 정도** 됩니다. 예를 들어 check engine lamp는 CAN type을 쓸 수도 있고 HW type을 쓸 수도 있습니다.
- 지금까지 다양한 고객사와 장비를 개발해 오면서 **보안을 위해 고객사별로 통합 관리하지 않았습니다.**
- 이제 내부 보안이 강화되어 고객사별 통합 관리가 가능해졌습니다. 이를 바탕으로 **한국·유럽·미국 등 지역별, 굴삭기·지게차·발전기 등 장비 유형별로 주로 쓰는 option 특성**을 파악하고, 추가 개선이 가능한 항목을 검토하려고 합니다.

현재는 옵션 정보가 프로젝트(고객사·장비)별 문서나 엑셀에 흩어져 있어, 여러 고객사를 가로질러 비교하기 어려운 것으로 보입니다(가정). 옵션 항목 자체도 앞으로 늘어날 수 있어 **항목을 담당자가 직접 추가할 수 있어야** 합니다.

## 2. 목표

### 2.1 최종 목표

- 고객사·장비별 인터페이스 옵션 선택 내역을 **한 곳에서 통합 관리**하는 도구
- **고객사·지역·장비 유형별로 많이 사용하는 옵션**을 표와 그래프로 보여 주어, 표준화·개선 후보 옵션을 찾는 데 쓰는 분석 화면

### 2.2 1차 개발 목표

- **옵션 카탈로그(항목·선택지 정의)를 화면에서 직접 추가·수정**할 수 있는 브라우저 도구를 먼저 만듭니다. 코드를 고치지 않고 담당자가 항목을 늘릴 수 있게 하는 것이 핵심입니다.
- 카탈로그를 기준으로 **고객사·engine suffix·장비 유형·지역·출력 등 레코드를 입력**하고, **엑셀로 가져오기·내보내기**합니다.
- **고객사·지역·장비 유형별 옵션 사용 빈도·비율**을 피벗 표와 막대그래프로 보여 줍니다.
- 모든 데이터는 **브라우저와 로컬 파일 안에만** 두어 고객사 정보가 외부로 나가지 않게 합니다.

## 3. 보유 데이터

| 데이터 | 형태 | 규모·주기 | 비고(민감도 등) |
|---|---|---|---|
| 고객사·장비별 인터페이스 옵션 내역 | 형태 미상(엑셀·사양 문서로 가정) | 항목 15개 정도, 항목별 선택지 2~5가지 정도. 레코드(고객사×장비) 수 미상 | **고객사 정보 — 보안 대상.** 지금까지 고객사별로 분리 관리해 왔음 |
| 옵션 항목 목록 | 담당자 정의 | **2026-09-29 확정: 기본 정보 5개 + 옵션 13개**(11장). 추후 담당자가 임의로 추가 | 1단계 제출 원문 예시(CAN SA, Pedal type 등)는 9-29 목록으로 바뀜 |

제출 원문의 항목 중 **고객사·engine suffix·장비 유형·출력**은 레코드를 구분하는 기본 정보로, **ATS type·CAN SA·Pedal type·starter control type·check engine lamp** 등은 선택지를 고르는 옵션으로 나누어 다룹니다(가정). 지역(한국·유럽·미국 등)은 원문 현안에 나오지만 항목 목록에는 없어, 기본 정보에 추가하는 것으로 봅니다(가정).

처음 제출에는 첨부가 없었고, 2026-09-29 수강생이 이 도구의 카탈로그 화면을 직접 고쳐 항목·선택지를 구체화해 보냈습니다. 이 목록으로 카탈로그 초기값을 확정했습니다(11장). 기존 정리 파일(엑셀) 형태는 아직 받지 못했습니다(10장 2번).

**개발 형태(권장)**

- **설치 없이 브라우저에서 도는 정적 웹 도구**로 만듭니다. 데이터는 **브라우저 저장소와 담당자 PC의 로컬 파일에만** 두고 서버·클라우드로 보내지 않으므로 **고객사 정보가 외부로 나가지 않습니다.** 원문에서 보안을 이유로 통합 관리를 미뤄 왔다고 했으므로 이 점을 가장 우선합니다.
- 집계는 건수·비율 계산이라 AI 서비스가 필요 없습니다.
- 브라우저 저장소는 브라우저 데이터를 지우면 함께 사라지므로, **로컬 파일 백업을 기본 작업 흐름**으로 둡니다. 여러 사람이 함께 쓰려면 사내 공유 폴더의 파일을 주고받는 방식을 먼저 검토합니다(가정 — 사내 보안 기준 확인 필요).
- AI 요약은 고객사명을 뺀 집계 숫자만 넘기는 방식으로 선택 기능으로 둡니다(외부 AI 사용 허용 여부 확인 필요).

## 8. 개발 단계

### 1단계 — 지금 바로 개발 가능한 부분

항목 구성이 담당자 정의로 바뀔 수 있다는 점이 원문의 핵심 요구이므로, **실제 항목 목록을 받기 전에도 카탈로그를 편집할 수 있는 구조**로 먼저 만들 수 있습니다.

- 옵션 카탈로그 편집 화면(항목·선택지 추가·수정·숨김) — 초기값은 원문 예시(ATS type, CAN SA, Pedal type, starter control type, check engine lamp: CAN type / HW type)로 채움
- 레코드 입력 화면(고객사·engine suffix·장비 유형·지역·출력 + 옵션 선택)
- 엑셀 가져오기(열 매핑)·내보내기
- 옵션별 사용 빈도·비율, 고객사·지역·장비 유형별 피벗 표와 그래프
- 브라우저 로컬 저장과 로컬 파일 백업·복원
- 시험용으로는 가상의 고객사·장비 레코드를 만들어, 일부러 지역·장비 유형별로 치우친 선택을 넣어 분석 화면이 그 차이를 보여 주는지 확인합니다.

### 2단계

- 실제 옵션 항목·선택지 목록과 기존 엑셀로 카탈로그 초기값·가져오기 보정
- 옵션 조합 분석, 출력 구간별 분석
- 변경 이력 기록, 표준 사양 후보 표시

### 3단계

- 개선 검토 결과(표준화 제안 등)를 레코드에 연결해 관리
- AI 요약 보고서, 사양서 기반 질의(Dify), 정기 보고서 배포(Make) — 모두 사내 보안 기준 허용 범위 안에서

## 9. 기대 효과

- **옵션 정보 통합** — 고객사별로 흩어져 있던 옵션 선택 내역을 같은 기준으로 한 곳에 모읍니다.
- **지역·장비 유형별 특성 파악** — 어느 지역·장비에서 어떤 선택지를 주로 쓰는지 표와 그래프로 바로 확인합니다.
- **개선·표준화 검토 근거 확보** — 사용이 드문 선택지나 한쪽으로 몰린 옵션을 찾아 개선 후보를 검토하는 근거가 됩니다.
- **항목 확장 용이** — 새 옵션 항목이 생겨도 코드 수정 없이 담당자가 바로 추가합니다.
- **보안 유지** — 데이터가 브라우저와 로컬 파일 밖으로 나가지 않습니다.

제출 자료에는 정량 수치가 없어 이 문서도 수치를 적지 않습니다.

## 11. 2026-09-29 옵션 항목 구체화

### 11.1 원문

> option 항목을 구체화 하였습니다.

첨부: 「인터페이스 옵션 관리」 PDF 7쪽 — 이 도구의 「옵션 카탈로그」 화면을 수강생이 직접 고친 뒤 인쇄한 것. 옮긴 목록은 `docs/source/2026-09-29_패들릿_추가요청.md`.

**공개 리포에 넣은 범위(판단 근거).** 첨부는 도구 화면 인쇄본이라 **항목 이름·선택지 이름·순서**만 담고 있습니다. 화면의 건수(72건·32건 등)는 이 도구의 **가상 예시 데이터**로 센 값이고, 실제 고객사명·레코드·사내 수치는 없습니다. 항목·선택지 이름은 J1939 메시지명(EEC2·TSC1·CCVS)·배출 규제 단계처럼 업계 공통 용어라 그대로 넣었습니다. PDF 원본은 리포에 넣지 않았습니다(목록으로 전부 옮겼으므로 필요 없음).

### 11.2 확정된 카탈로그 (도구 초기값)

| 구분 | 항목 | 선택지 |
|---|---|---|
| 기본 정보 | 고객사(필수) · engine suffix · 출력 | 글자·숫자 |
| 기본 정보 | **Machine type** (1단계 「장비 유형」) | Excavator · Forklift · Generator · Loader · TLS |
| 기본 정보 | **Emission regulation** (1단계 「지역」) | Korea Stage5 · EU Stage5 · NA Tier4f · EU Stage3A · Unregulated |
| 옵션 | ATS type | DOC+DPF · DOC_SDPF · DOC · Muffler |
| 옵션 | CAN1(J1939) baudrate | 250kb · 500kb |
| 옵션 | Accelerator type | CAN (SMVCU) · CAN (EEC2) · CAN (TSC1) · Hardwire Foot · Hardwire Foot and Hand |
| 옵션 | starter control type | VCU control · ECU control |
| 옵션 | check engine lamp | CAN type · HW type |
| 옵션 | Parking Brake | CAN (CCVS) · CAN (SMVCU) · Hardwire (Normally open) · Hardwire (Normally closed) |
| 옵션 | SAC lamp · Emergency stop · Regeneration demand switch · Regeneration inhibit switch | CAN · Hardwire |
| 옵션 | Oil pressure lamp | (선택지 없음 — 원문 그대로 비워 둠) |
| 옵션 | WIF · Electric feed pump | VCU · ECU |

- 옵션은 13개(1단계 원문 「15가지 정도」와 비슷), 선택지는 2~5개로 원문 설명과 맞습니다.
- 항목·선택지 id 는 1단계와 이어지게 두었습니다(장비 유형 → Machine type 은 `f_equip`, 지역 → Emission regulation 은 `f_region` 그대로). 선택지 id 로 저장하므로 이름을 고쳐도 기존 레코드가 따라옵니다.
- **항목 추가는 그대로 됩니다**(원래 요구). 카탈로그 화면·Excel 가져오기 「새 옵션 항목으로 추가」 모두 유지.
- 분석 기준 「지역별」은 **Emission regulation 별**로 봅니다. 배출 규제가 시장(한국·EU·북미)을 나타내므로 지역 역할을 한다고 판단했습니다(11.4 확인 1).

### 11.3 반영 방식

| 요청·지시 | 반영 |
|---|---|
| 첨부 카탈로그를 도구의 옵션 정의(기본 스키마)에 반영 | `defaultCatalog()` 를 11.2 표로 교체. 테스트가 항목·선택지 이름과 순서를 원문과 대조 |
| 항목 추가 가능 유지 | 그대로. 테스트 「항목 추가는 여전히 가능 — 14번째 옵션」 |
| 옵션 간 제약을 규칙으로 | **「적용 조건」** 기능 추가 — 「옵션 X 는 항목 Y 가 이 선택지일 때만 씀」. 카탈로그 화면에서 추가·삭제. 조건에 맞지 않으면 입력 칸이 잠기고, 집계에는 **「(해당 없음)」으로 미입력과 따로** 세며 최다 선택지 후보에서 뺍니다. 이미 들어간 값이 조건에 어긋나면 **지우지 않고** 목록에서 알려 줍니다(「해당 레코드만 보기」). 백업·Excel(「적용 조건」 시트)에 함께 담김 |
| 초기 적용 조건 3개(가정) | 첨부에 제약이 적혀 있지 않아 **엔진 인터페이스 상식으로 둔 가정**입니다. ① Regeneration demand switch ② Regeneration inhibit switch — ATS type 이 DPF 가 있는 DOC+DPF·DOC_SDPF 일 때만(재생은 DPF 가 있어야 의미가 있음) ③ Parking Brake — Machine type 이 Generator 가 아닐 때만(주행하지 않는 장비). 틀리면 화면에서 지우면 됩니다 |
| 다빈도 옵션 집계 예시 데이터 재작성 | 새 항목 기준 **가상 고객사 8곳 × 12건 = 96건**. 5개 Machine type·5개 Emission regulation 이 모두 나오고, 규제·장비별로 일부러 치우친 선택(예: EU Stage5 → DOC_SDPF·500kb, Unregulated → Muffler·HW type, Forklift → Hardwire Foot, Generator → ECU control)을 넣어 분석 화면이 차이를 보여 주는지 확인. 적용 조건을 어기는 값은 없음(테스트). 예시 파일(`samples/`)도 다시 만듦 |
| DB 스크립트 | `supabase/schema.sql` 에 `catalog_rule` 표 추가(RLS·변경 기록·재실행 안전). 로컬 PostgreSQL 에서 이전 판 위에 올리기·재실행·제약·타인 격리 확인 |
| 이미 쓰던 브라우저 | 저장된 카탈로그는 그대로 둡니다(담당자가 고친 것을 덮어쓰지 않음). 옛 판 카탈로그면 카탈로그 화면 위에 「예시 데이터 불러오기 / 백업 후 모두 지우기로 새 카탈로그」 안내가 나옵니다 |

### 11.4 남은 확인 사항

1. **Emission regulation 을 지역 대신 쓰는지** — 지역(한국·유럽·미국) 항목을 따로 두지 않고 배출 규제로 지역 분석을 대신해도 되는지. 따로 필요하면 기본 정보 항목으로 추가하면 됩니다.
2. **적용 조건 3개가 맞는지**(11.3 가정) — 그리고 그 밖에 장비 유형·배출 규제에 따라 쓰지 않는 옵션이 있는지(예: Unregulated 에서 Regeneration 스위치, Generator 의 Accelerator type).
3. **Oil pressure lamp 의 선택지** — 다른 램프처럼 CAN · Hardwire 인지.
4. **「DOC_SDPF」 표기** — 원문 그대로 두었습니다. 「DOC+SDPF」의 오타라면 카탈로그에서 이름만 고치면 기존 레코드도 함께 바뀝니다.
5. 10장 2·3번(기존 정리 엑셀 형태, 레코드 1건의 단위)은 아직 남아 있습니다.
