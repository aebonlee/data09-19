# Supabase DB 스크립트 — 엔진 인터페이스 옵션 통합 관리·분석 도구

이 폴더에는 옵션 카탈로그와 옵션 내역을 데이터베이스(Supabase)에 저장할 때 쓰는 SQL 스크립트가 들어 있습니다.
지금 도구는 이 스크립트 없이도 그대로 동작합니다.
앱을 DB 에 연결하는 일은 다음 단계에서 진행합니다.

> **먼저 확인할 것 — 고객사 정보는 보안 대상입니다(기획서 3장).**
> 지금 도구는 고객사 정보가 브라우저와 내 PC 밖으로 나가지 않도록 만들었습니다(기획서 7장).
> DB 에 올리면 자료가 클라우드에 저장되므로, **사내 보안 기준에서 허용된 뒤에만** 연결합니다.
> 이 스크립트는 그때 바로 쓸 수 있도록 미리 준비해 둔 것입니다.

## 왜 DB 가 필요한가

지금 도구는 옵션 카탈로그(항목·선택지·적용 조건), 옵션 내역, 열 연결을 브라우저 저장소(localStorage)에만 둡니다.
이 방식에는 다음과 같은 한계가 있습니다.

- **변경 이력이 남지 않습니다.** 기획서 5장·8장 2단계의 「변경 이력 — 카탈로그·레코드 수정 시 언제 무엇이 바뀌었는지 기록」은 브라우저 저장소로는 믿을 수 있게 남길 수 없습니다. 지금은 마지막 상태만 저장됩니다.
- **담당자끼리 같은 카탈로그를 쓰기 어렵습니다.** 지금은 백업 파일(JSON)이나 Excel 을 주고받아야 해서, 누가 어느 판을 갖고 있는지 흐트러지기 쉽습니다.
- **브라우저 데이터를 지우면 사라집니다.** 백업 파일을 저장하지 않았다면 되살릴 수 없습니다.
- **다른 PC 에서는 백업 파일을 다시 불러와야 합니다.**

## 테이블

| 테이블 | 용도 | localStorage 대응 (`data09-19.db`) |
|---|---|---|
| `catalog_field` | 카탈로그 항목(고객사·engine suffix·Machine type … / ATS type·check engine lamp …), 기본 정보·옵션 구분, 글자·선택 목록·숫자, 필수 여부, 숨김, 순서 | `catalog.fields[]` |
| `catalog_choice` | 항목별 선택지(예: check engine lamp → CAN type / HW type), 숨김, 순서 | `catalog.fields[].choices[]` |
| `catalog_rule` | 적용 조건 — 「옵션 X 는 항목 Y 가 이 선택지일 때만 쓴다」 | `catalog.rules[]` |
| `option_record` | 옵션 내역 한 건(고객사×장비), 항목 id → 값 | `records[]` |
| `column_mapping` | 엑셀 열 이름 ↔ 카탈로그 항목 연결(다음 가져오기에 재사용), 사용자당 한 행 | `mapping` |
| `change_log` | 카탈로그·레코드 변경 기록(언제, 어느 표의 무엇이, 이전 값·이후 값) | 없음(새로 추가, 2단계 「변경 이력」용) |

지켜지는 규칙은 다음과 같습니다.

- 도구와 같은 규칙을 DB 도 지킵니다.
  - 옵션 항목은 언제나 선택 목록입니다.
  - 대소문자·공백·밑줄·하이픈·점·가운뎃점·빗금만 다른 항목 이름은 같은 항목으로 보고 두 번 받지 않습니다. 선택지 이름도 한 항목 안에서 같은 방식으로 봅니다.
  - 선택지는 선택 목록 항목에만 붙습니다.
  - 적용 조건은 자기 자신을 조건으로 삼을 수 없고, 같은 (옵션, 조건 항목) 쌍은 한 번만 만들 수 있으며, 선택지를 하나 이상 골라야 합니다.
  - 고객사가 빈 레코드는 받지 않습니다.
- 항목·선택지는 지우지 않고 숨깁니다(`active = false`). 과거 기록과 집계를 보존하기 위해서입니다(기획서 5장).
- 레코드는 선택지를 id 로 저장합니다. 선택지 이름을 고쳐도 기존 레코드가 그대로 따라옵니다.
- 레코드 값은 `jsonb` 한 칸에 둡니다. 담당자가 항목을 늘릴 때마다 표 구조를 바꾸지 않아도 되게 하기 위해서입니다.
- 항목·선택지·적용 조건·레코드를 만들거나 고치거나 지우면 **트리거가 `change_log` 에 자동으로 기록**합니다. 앱이 따로 기록할 필요가 없습니다. 원래 행을 지워도 기록은 남습니다.
- 앱에서 upsert 할 때 지정할 `onConflict` 값: `catalog_field` 는 `owner_id,field_key`, `catalog_choice` 는 `owner_id,choice_key`, `catalog_rule` 은 `owner_id,rule_key`, `option_record` 는 `owner_id,record_key`, `column_mapping` 은 `owner_id`.

## 보안

- 모든 테이블에 행 수준 보안(RLS)이 켜져 있습니다.
- 모든 행은 만든 사람(`owner_id`)만 보고 고칩니다. `owner_id` 는 로그인한 사용자로 자동으로 채워집니다.
- 다른 사람의 항목에 선택지를 끼워 넣거나, 다른 사람 이름으로 행을 넣을 수 없습니다.
- 로그인하지 않은 방문자(anon)는 아무것도 보거나 쓸 수 없습니다.
- `change_log` 는 기록용이라 본인도 수정·삭제할 수 없습니다(추가·조회만 가능).
- 함수는 `search_path` 를 고정했고, 실행 권한을 로그인 사용자에게만 줍니다. 이 스키마에는 RLS 정책에서 쓰는 판정 함수가 없으므로 anon 에게 실행 권한을 남긴 함수도 없습니다.

## 적용 방법

1. <https://supabase.com> 에 가입합니다.
2. 새 프로젝트(New project)를 만듭니다. 본인 계정의 본인 프로젝트에 적용합니다.
3. 왼쪽 메뉴에서 SQL Editor 를 엽니다.
4. `supabase/schema.sql` 파일 내용을 전부 복사해 붙여 넣습니다.
5. Run 을 눌러 실행합니다.

여러 번 실행해도 안전합니다. 이미 있는 테이블·정책은 건너뛰거나 새로 고쳐 만듭니다.

## 확인 방법

- Table Editor 에 위 표의 테이블 6개가 보이면 됩니다.
- Authentication → Policies 에서 6개 테이블 모두 RLS 가 켜져 있고 정책이 붙어 있는지 확인합니다.
- SQL Editor 에서 다음을 실행하면 정책 22개가 나와야 합니다.

  ```sql
  select tablename, policyname, cmd from pg_policies where schemaname = 'public' order by 1, 2;
  ```

## 앱 연결은 다음 단계입니다

이번에는 스크립트만 저장했습니다.
도구의 `js/store.js` 는 아직 localStorage 를 씁니다.
연결할 때는 사내 보안 기준 허용을 먼저 확인하고, 본인 프로젝트의 URL 과 anon 키를 받아 로그인 기능과 함께 붙입니다.

## 로컬 검증 방법

운영 DB 에 올리기 전에 내 컴퓨터의 임시 PostgreSQL 에서 스크립트를 실제로 적용해 확인할 수 있습니다.

```sh
./scripts/sqltest/run.sh
```

- PostgreSQL 16·17 이 필요합니다(macOS: `brew install postgresql@17`).
- 임시 데이터베이스를 만들어 쓰고 끝나면 지우므로 기존 설치에 영향이 없습니다.
- 스키마를 두 번 적용해 재실행 안전성을 보고, 사용자 A·사용자 B·비로그인 세 역할로 RLS 격리·제약·변경 기록 트리거·기록성 표·함수 권한을 확인합니다.
- 마지막에 「SQL 검증 통과.」가 나오면 성공입니다.
- `scripts/sqltest/*.local.sql` 은 로컬 검증 전용입니다. Supabase SQL Editor 에서 실행하면 스스로 멈추도록 가드가 들어 있습니다.
